## 一、结论先行

1. **安全语义缺口：通知没有分级。** 全仓没有 `interruptionLevel`，烟感、漏水告警和「错过的定时」是同一档；专注模式的信号已经拿到，却没用来压低非关键通知（R16）✅。
2. **最大的流失点在应用之外。**
   - 旧仓 `jryang1997/MenuBarMijia` 已 404，新仓只有 44★（R09）✅。
   - 官方 1.4.0 DMG 下载 16 次，而 1.2.0 / 1.3.0 分别是 107 / 84 次（R08）✅。
   - 「已登录但 0 设备」两个来源独立复现过，是唯一被反复证实的卸载原因（#67、#76）。
3. **空闲耗电还有低垂果实。**
   - 菜单栏 0.5 s 标签定时器和分钟级唤醒定时器都没设 `tolerance`（R10）✅。
   - 安全检查是常驻的 60 s `Task.sleep` 循环 ✅。
   - 轮询只有 3 档（R10）。
4. **两端平行实现是长期病根。**
   - 电视/机顶盒认领两端不一致，已登记在 `windowsDivergences`（R03）✅，说明双份代码只能「记账」差异，没法消灭。
   - 112 条标题文字两端逐字重复（R03）○。
   - 建议走「共享数据只放选择、不放计算」。
5. **多平台适配的前置条件还没满足。**
   - `activeBackends` 写死两个布尔参数（R04）✅。
   - Windows `HomeProvider` 只有 `execute` 一个方法（R05）✅。
   - 在接第三个源、做外部插件之前，要先把这两处改成能容纳 N 个源。
6. **Magpie 的插件机制，组织方式值得学，防护方式不能抄**（R12）。
   - 它的 Bun 插件拥有宿主同等权限，官方原话是 "install trusted code"。
   - 没有代码签名。
   - 我们控制的是物理设备，插件必须在宿主进程外运行，写入门、确认、锁屏、凭据都留在宿主手里（R02、R05、R12、R13 结论一致）。
7. **口令解析有确定的错。**
   - 「冷光」我们是 6500K，HA 中文语料是 4000K ✅。
   - 风扇百分比能力已经有了，只是解析器没接上（R14）◐。
   - 黄金语料我们只有 52 条，HA 中文有 768 条带槽位标注的句子。
8. **Windows 端有一个确认的布局缺陷**：任务栏自动隐藏时，面板会被任务栏盖住。另外每发一条通知都要拉起一次 `powershell.exe`，点通知也没反应（R07）✅。

## 二、对子报告的更正与冲突

- **CPU**：R08 说「CPU 1%→11%，FAQ 还写 0.1%」。这个问题已被 PR #208（2026-11-17 合入）修复。现状是修复后没人复测，0.1% 缺数据支撑，而不是文档与现状矛盾 ✅。
- **呼吸点动效**：R11 建议「点亮 `BreathingDot`」，但它正是 #208 的根因。要启用，必须保留「面板不可见即停」的规则。
- **滚动区玻璃容器**：R11 建议移除滚动区外层的 `AdaptiveGlassContainer`（`ControlCenterPanelLayout.swift:700`），理由是性能风险，但没有测过帧率；去掉还会改变卡片边缘的融合效果。先量再改，降为 P1。
- **60 s 安全循环**：R10 标成「非高风险」，但这条循环承载漏水、烟雾告警，改错的后果是漏报。按高风险走 PR，并补「告警不延迟」测试。
- **摄像机桥**：R15 说 go2rtc `msgClose` 补丁「不改控制写入」，但改的是随安装包分发的二进制，影响打包链路，走 PR，并且要真机计时。
- **issue**：R07、R14 建议直接开 issue。按你的要求，本轮不开。

## 四、插件化路线（合并 R02、R05、R12、R13）

所有阶段共守一条边界：**宿主进程内不跑第三方代码；写入门、危险分级、二次确认、锁屏拦截、凭据库永远归宿主**。这与 ADR-0020/0023 一致，只是启用了 ADR 里预留的「进程外扩展」重启条件。

| 阶段 | 内容 | 对外面 |
|---|---|---|
| 0（现在可做） | 内部先能容纳 N 个源：`activeBackends` 参数化、错误码归一、capabilities 声明、Windows `HomeProvider` 补齐（清单 #12、#25） | 无 |
| 1 | 加深只读扩展面：MCP `--read-only`、Alfred/SwiftBar 输出、Raycast AI tools（#9、#31） | 读快照 + `menumijia://` |
| 2 | 通用子进程监督器（#24），先让 go2rtc 受益 | 内部 |
| 3 | ADR-0024《进程外适配器协议 v0》：stdio JSON-RPC、manifest 字段表（含禁止字段）、设备身份与 `sourceScope = adapter:<id>`、凭据只给短期租约 | 契约 |
| 4 | 只读参考适配器（LG webOS），顺带清理 LG 绕开 `HomeProvider` 的历史特例 | 第一个外部进程 |
| 5 | 写能力：`control.execute` 只在宿主写入门之后发出，带 `grantId` 与能力代次 | 可控 |
| 6 | Ed25519 签名 + 权限扩张时再确认 + blocklist，之后才谈市场 | 分发 |

从 Magpie 可以直接借的：
- 声明式能力（provider 声明模型发现、登录方式、额度和健康状态）。
- 窄 RPC 接口。
- 按账号区分作用域。
- 失败语义分层（崩溃、超时、内存回收）。
- 「审核列表 + 下架」的运营模式。

不能借的：
- 宿主同等权限。
- 进程内中间件。
- 没有签名。

## 五、明确不做

- 宿主进程内加载第三方插件，以及插件自带 HTML/JS 页面（R12、R02）。
- 换回 `MenuBarExtra`、引入 Sparkle、用私有 API 隐藏别人的菜单栏图标（R10）。
- 小度、天猫精灵、华为 HiLink、萤石，以及任何厂商的纯「云轮询」形态（R04）。
- 借用涂鸦扫码 SDK 里写死的 HA `client_id`，会重蹈 ADR-0014 的覆辙（R04）。
- 高风险确认加「按设备不再询问」（R08 #5）。我的意见是不做：这条会把安全判决交给一次点击。确认弹得太多的问题，应该靠收窄判定范围解决（例如已有的「这是灯」标记），而不是给确认开后门。

## 六、需要拍板

1. **签名公证**：要不要买 Apple Developer ID（每年 99 美元）并做 Windows 签名。这是首装拦截的根治办法，也是 Matter 和 Widget 的前置条件。
2. **对外动作**：要不要授权去 `awesome-mac`、Scoop 等外部列表提交「旧名 → 新仓」的链接更正。
3. **新厂商投入**：先估算「没装 HA 的用户比例」再决定要不要做涂鸦本地，还是直接把预算投到 HA 侧体验。
4. **插件化**：是否启动第四节阶段 3，即只写 ADR 和契约、不写运行时代码。
5. **口令取值**：最暗亮度定 1%（社区语料）还是 10%（我们现在）。

**2026-11-23 拍板结果**：
1. 签名公证先不做，#3 的安装页截图提前做。
2. 外部链接授权更正：先起草 PR 内容，用户看过后再发。
3. 插件化先做内部打地基（#12、#25），ADR-0024 之后再写。
4. 最暗亮度改为 1%，并入 #7。
5. 新厂商投入还没定。

## 七、设想（天马行空，挑最有意思的）

- **「家的菜单栏读数」**：菜单栏图标本身就是数据面，显示室温、开着几盏灯、告警红点，点开面板之前就知道家里怎样了（R09、R11、R07）。
- **桌面变成家的「活动流」**：门铃、洗衣机还剩 15 分钟、撤销倒计时，做成菜单栏旁的实时胶囊，类比 Live Activity（R06）。
- **反向进入 Apple 家庭**：用 HAP 虚拟桥把米家设备「借」进 Apple 家庭和 Siri，不需要 HomeKit 权限（R05）。
- **一次声明，两端生效**：设备规则、文字、能力全部数据化，再由 schema 生成 Swift/TS 类型，双端差异从「记账」变成「编译不过」（R03）。
- **适配器即 npm 包**：照 Magpie 的形态，社区用 TS 写平台适配器，跑在受监督的子进程里，宿主只交给它短期凭据租约（R12）。

## 八、局限

- 米家、Aqara、SmartThings、涂鸦 App 的一手界面资料没查到（R16）。
- 我们手上没有中枢网关、多模网关、VRF 内机这些实机，相关能不能做都来自上游源码和用户复现（R01）。
- 社区评价大多来自搜索摘要，原话以各报告附的链接为准（R09）。
- ○ 项交付实施前要逐条复核行号。
