# 全设备覆盖：现状量化与方案

调研日期：2026-11-05　前置阅读：[2026-11-05-ecosystem-benchmark.md](2026-11-05-ecosystem-benchmark.md)（同行源码对标）、[miot-unsupported-categories.md](miot-unsupported-categories.md)（10-31 的头部品类清单）
本文回答一个问题：**米家全部设备，我们到底覆盖了多少，怎样做到近乎全覆盖，而不是一个品类一个品类地补。**

标注：**【复算】** 跑了脚本；**【源码】** 读了实现；**【推断】** 我的判断。

---

## 0. 结论先行

1. **近三成型号现在没有可用卡片。** 对 MIoT 规格库全部 14,927 个型号（177 个设备类型）按本项目 `primary(for:)` 的逻辑逐类重放：
   - 类型对得上、有卡片的约 **68%**；
   - **被静默丢弃但其实可控**约 **24%**（≈3,500 个型号）；
   - 丢弃且只读约 2.5%；
   - 规格里没有任何可用属性约 2.8%；
   - **被误判成别的设备类型约 2.8%**（这是安全问题，见 §3）。
2. **这是长尾问题，不是头部问题。** 有丢弃的设备类型多达 **134 个**。前 10 个类型占丢弃量的约 62%，前 20 个占约 80%，剩下 114 个类型合起来还有两成。一个品类补一个 builder 永远补不完。
3. **已经"支持"的设备也只用了一小部分。** 原生支持的型号平均还有约 **8.4 个可写控件**（开关、枚举、滑块）没有暴露（上限估计，含部分设置类噪声）。
4. **HA 通道的缺口更大。** `DeviceSynthesizer` 的主实体域是白名单：`light/climate/fan/vacuum/camera/switch/media_player/sensor/binary_sensor/button`。`cover`、`humidifier`、`water_heater`、`valve`、`event` 一个都没处理，全部落入"实体类型暂不支持"。用官方集成的 HA 用户同样看不到窗帘、加湿器、热水器。
5. **能规模化的是"形状"，不是"品类"。** 头部被丢弃的类型集中在少数几种控制形状上：电机（窗帘/晾衣架/电动桌）、家电（洗衣机/洗碗机/烘干机/热水器/浴霸/油烟机…，同形：电源 + 模式 + 状态 + 故障 + 目标温度 + 剩余时间）、纯只读（净水器/体重秤/路由器/网关）、纯动作（遥控器/电视/机顶盒）。5 个形状加一个通用兜底，就能覆盖几乎全部。方案见 §5。

## 1. 方法与口径

- 数据：`miot-spec.org` 的 `instances?status=released`，取每个型号的最新版本，共 14,927 型号、177 个设备类型。
- 规格：每个设备类型随机抽至多 6 个型号拉真实规格，共 812 份；类型内的比例按抽样外推到该类型的全部型号。**小类型（≤6 个型号）是全量，大类型（如 `switch` 3,207 个）是抽样，误差可观。** 所有百分比只代表数量级。
- 判定：把 `MiotSynthesizer.primary(for:)` 完整复现为 Python：先按设备类型名在注册表找服务，再按注册表顺序回退（`light` 副服务有排除规则，`electronic-valve` 仅在有电功率时认领），最后是传感器的 `environment` 回退。
- "可控"：有可写的布尔/枚举/范围属性，或有动作；"只读"：只有可读的非字符串属性。
- "噪声过滤"：去掉 `device-information`、`exception-card`、`device-custom` 及所有 `*-custom` 服务（厂商私有）。
- 复算用的一次性脚本和 812 份样本没有放进仓库。可复现的版本由 [#295](https://github.com/jryang1997/MenuBarMijia/issues/295)（覆盖率基线）以测试夹具的形式落地，届时以它为准。
- 本文对应的工单：[#295](https://github.com/jryang1997/MenuBarMijia/issues/295)–[#310](https://github.com/jryang1997/MenuBarMijia/issues/310)，总括单 [#188](https://github.com/jryang1997/MenuBarMijia/issues/188)。

## 3. 误判：不是"没做"，而是"做错了"【复算】

当前回退逻辑是"注册表里任何一个服务存在就认领"。这会让**设备类型与主服务不一致**的设备被画成别的东西：

| 设备类型 | 型号 | 被画成 | 风险 |
| --- | ---: | --- | --- |
| 投影仪 `projector` | 137 | 音箱（`speaker`） | 显示音量/静音，没有电源 |
| 电视 `television` | 90 中约 2/3 | 音箱 | 同上 |
| 电视盒 / 故事机 / 拖地机 / 宠物喂食器 | 12 / 5 / 11 / 25 中一部分 | 音箱 | 同上 |
| **驱虫器 `insect-killer`** | 14 | **扫地机 / 空调 / 摄像头** | 命令会按错误的设备类型下发 |
| 玩具 `pet-toy` | 12 | 扫地机 | 同上 |
| 鱼缸 `fish-tank` | 14 | 暖风机（部分型号） | 水泵与灯光不可见 |
| 门 `door` | 25 | 门锁 / 门铃 | 可接受 |
| 继电器 `relay` | 7 | 开关 | 可接受 |
| 锅炉 `boiler`、测距仪 | 11、29 | 恒温器 | 目标温度语义可能不对 |

约 **2.8%** 的型号（≈420）受影响。其中"驱虫器变扫地机卡片"这类会让用户对一个不是扫地机的设备点"开始清扫"，属于应当先于覆盖率修掉的缺陷。**修法不是加规则，而是让回退认领必须经过"类型兼容表"**（§5.2 第 2 级）。

## 4. 同行怎样做到近乎全覆盖（回顾源码结论）

详见对标文档 §3。要点：

- **官方 `ha_xiaomi_home`**：设备级声明表（必需/可选服务与属性）→ 属性级通用兜底（按"格式 + 读写"）→ 事件与动作 → `spec_filter / spec_modify / spec_add` 型号修补。可写但既不是枚举也不是范围的属性直接跳过。【源码】
- **al-one**：3,914 行型号覆盖，键支持通配符（`*.fishbowl.*`、`*.cateye.*`），可以逐属性指定为 sensor / switch / select / number / button，或排除。【源码】
- **homebridge-miot**：解析阶梯，型号类 → 规格类型 → 通用设备 → 未知设备，永远有落点。【源码】
- **Itsyhome**：每种类型一个手写菜单项，没有通用兜底，所以覆盖面反而比我们窄；但它做的是"少而精"。【源码】

**共同点**：覆盖率来自**兜底层**，精致度来自**类型层**，两层独立演进。我们只有类型层，而且类型层的回退还会误判。

## 5. 方案：形状 + 阶梯 + 通用控件 + 数据化覆盖

### 5.1 五个形状加一个兜底

不按"品类"建模，按**控制形状**建模。每个形状是一个"能力谓词 + 渲染"，设备规格命中哪个形状就套哪个。

| 形状 | 命中条件（谓词） | 渲染 | 覆盖的头部类型 | ≈型号 |
| --- | --- | --- | --- | ---: |
| **电机 Cover**（已有 `CoverSpec`，扩展） | 可写 `motor-control` 且枚举含开/关词，或可写范围型 `target-position` | 开/停/关 + 位置滑块 + 开合中状态 | 窗帘、晾衣架、电机控制器、窗户、电动桌（部分） | ≈1,250（8%） |
| **家电 Appliance**（新） | 可选 `on`；以及 `mode`、`status`、`fault`、`target-temperature`、`left-time`、无参 `start/pause` 动作中至少两项 | 电源 + 模式选择 + 状态文案 + 故障条 + 目标温度步进器 + 剩余时间 | 洗衣机、烘干机、洗碗机、热水器、浴霸、油烟机、毛巾架、马桶、按摩、蒸烤箱等 | ≈1,200（8%） |
| **读数 Readout**（扩展 `SensorSpec`） | 无可写控件，有可读数值/枚举 | 主读数 + 副读数列表 + 滤芯/电量徽标 | 净水器、体重秤、路由器、网关、测距仪 | ≈600（4%） |
| **动作 Actions**（新） | 以无参动作为主，几乎无属性 | 按钮网格 | 遥控器、电视、机顶盒、手表、保险箱、滑板车 | ≈400（3%） |
| **复合 Composite**（新，= 主卡片 + facets） | 一个设备命中多个形状 | 主卡片取最强形状，其余作为抽屉内的控件 | 鱼缸、喂食器、浴霸（灯 + 风暖 + 换气）、冰箱多室… | — |
| **通用兜底 Generic**（新） | 以上都不命中，但有可控面 | 名称 + 房间 + 关键读数 + 通用控件抽屉 | 134 个类型里的长尾 | ≈10%+ |

已有的 `light/climate/fan/plug/vacuum/speaker/tv/camera/sensor/fridge` 保持不变，它们是"精致的类型层"，对应形状谓词只是把现有 builder 的触发条件显式化。

### 5.2 解析阶梯（永远有落点）

```
1. 型号覆盖        数据表按型号/通配符命中 → 直接给出 形状 + 绑定 + 排除 + 怪癖
2. 类型 + 兼容表   设备类型名 → 首选服务；回退认领必须通过"类型兼容表"
                  （例：air-condition-outlet → air-conditioner，door → lock；
                   insect-killer/pet-toy 不得被 vacuum 认领）
3. 形状检测        按 §5.1 的谓词在整份规格里找形状
4. 通用控件        剩余属性按"格式 + 读写"自动生成 facets，过滤噪声
5. 兜底卡片        连属性都没有 → 显示"该设备没有向云端开放可控项"，附型号，供一键反馈
```

第 2 级修 §3 的误判；第 3–4 级把 24% 的"丢弃但可控"收回来；第 5 级让"未显示设备"只剩真正无规格的设备。

### 5.3 通用控件（facets）规则

直接采用官方集成已验证的"格式 + 读写"映射，并补上它没做的过滤：

| 规格 | facet |
| --- | --- |
| 可写 `bool` | toggle |
| 可写且有枚举 `value-list` | picker |
| 可写且有 `value-range` | slider（step 取规格值） |
| 可写但既无枚举也无范围 | **跳过**（官方同样跳过） |
| 只读数值/枚举/布尔 | readout（带单位、有换算说明的先换算，见 `docs/qa/device-compatibility-124-129.md` 的功率缩放） |
| 无入参动作 | action 按钮 |
| 有入参动作 | 仅当入参都是枚举/范围时生成带表单的 action，否则跳过 |
| 字符串属性 | 默认跳过（多为 JSON、时间段串、内部配置） |

**必须有的过滤层**（鱼缸规格里一半以上属性是内部项）：

- 服务级：`device-information`、`exception-card`、`device-custom`、所有 `*-custom`、`no-disturb*` 的内部子项；
- 属性级：`bind-timestamp`、`trigger-status`、`no-reminder-status`、`*-list`（JSON 串）、`code`、`*-time`（时间戳）；
- 展示级：每个设备默认只露出"主卡片 + 不超过 N 个高价值 facets"，其余折叠进"更多设置"。N 和高价值的判定（例如 `mode`、`target-*`、`*-level`、`brightness`）放进数据表，而不是写在代码里。

### 5.4 型号覆盖层数据化

沿用 `Sources/MijiaCore/Resources/fallbackSpecs.json` 的做法，新增一份**双端共享**的 `Sources/MijiaCore/Resources/deviceProfiles.json`：

```jsonc
{
  "types": { "curtain": {"shape": "cover"}, "airer": {"shape": "cover", "quirks": {"positionReverse": true, "labels": {"open": "升", "close": "降"}}} },
  "compat": { "air-condition-outlet": ["air-conditioner"], "door": ["lock","video-doorbell"] },
  "models": { "*.fishbowl.*": {"shape": "composite", "primary": "fish-tank", "highlight": ["water-pump","pump-flux","temperature","pet-food-out"]},
             "090615.curtain.*": {"exclude": ["motor-control"]} },
  "noise": { "services": ["exception-card","device-custom"], "properties": ["bind-timestamp","trigger-status"] }
}
```

Swift 与 TS 各写薄解释器，由 `Tests/Fixtures/miot_golden.json` 守一致（CODING_STANDARDS 第 6 条已要求）。这样新增一个型号怪癖是改数据，不是改两份 1,000 行的合成器。需要新 ADR，并与 ADR-0006 对齐。

### 5.5 HA 通道的同构补丁

HA 通道没有"规格"，但有实体域和 `device_class`。对称做法：

- 扩主实体域：`cover`、`humidifier`、`water_heater`、`valve`、`lock`（执行）、`event`；
- 未被主卡片认领的实体按域生成 facets：`switch` → toggle、`select` → picker、`number` → slider、`button` → action、`sensor/binary_sensor` → readout、`text` 跳过；
- 现状里的实体 ID 子串匹配（如 `contains("temperature_p_3")`、`contains("filter_life")`，见 `DeviceSynthesizer.swift:783-786`、`:708`）依赖官方集成的 `_p_<siid>_<piid>` 命名约定，换另一个 HA 集成会失配【推断：我没有核对 al-one 的实体 ID 格式】。应改为读实体的 `device_class` / `translation_key`。
- `event` 域 + `device_class: doorbell` 接上门铃（见对标文档 §4.3）。

### 5.6 把"覆盖率"变成可回归的数字

这是让"全覆盖"不退化的关键：

1. 把每个设备类型 1–2 份真实规格（≈180–350 份，压缩后体量可控）放进 `Tests/Fixtures/miot/`，只保留公开规格，不含账号信息（现有夹具已是这个做法）。
2. 加一个测试，对夹具全集断言：
   - **没有误判**：回退认领都通过兼容表；
   - **每个有可控面的类型都至少产生一张卡片**；
   - 各形状的命中数不低于基线（回归守卫）；
   - 噪声属性不出现在 facets 里。
3. 把 `scripts/check.sh` 里加一行输出"覆盖率报告"（原生 / 复合 / 通用 / 无可控面 各占比），PR 里可见变化。

## 6. 分阶段路线（每步有可衡量的结果）

## 7. 风险与非目标

- **通用卡片的易用性风险**：把 14 个控件一股脑摆出来比"不显示"更糟。所以 §5.3 的高价值判定和折叠必须一起做，不能只做规则引擎。
- **写操作的安全**：通用 facets 会让用户直接写设备属性（如路由器配置、烘干机加热）。高风险写入必须沿用现有 `ModelActionPolicy` 的确认表，默认对通用 facets 只开放"低风险白名单"（亮度、模式、风速等），其余需在设置里显式打开。
- **只读/不可控品类要诚实**：体重秤、手表、牙刷、保险箱等本就没有可写面，卡片应说明"只读"，而不是假装可控。
- **不做**：远程开锁、PTZ、双向语音（与此前结论一致）；小米私有蓝牙/ZigBee 直连（`ADR-0007` 仍然延期）。

## 8. 局限

- 抽样口径：每类至多 6 份规格，大类型外推误差大；"原生 68%"这类数字只能当数量级。
- 规格里**有**可写属性不等于云端**允许**写：部分设备的属性可写但云端会拒绝，必须真机验证后再放进白名单。
- 没有统计各型号在真实用户里的占比：型号数多不等于用户多。若有匿名的"未显示设备"诊断数据（`UnsupportedDeviceCollector` 已有），应以它为准调整阶段 1–3 的顺序。
- 没有真机验证。
