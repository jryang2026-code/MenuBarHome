# ADR-0015：不收集远端遥测，只提供本地脱敏诊断与崩溃摘要

日期：2026-11-07　状态：已接受（对应 #17，原 GitHub #183；关联 #45、ADR-0004、ADR-0012）

## 背景

#17 要求为「崩溃与功能使用统计」定一条隐私边界，用于决定后续功能的取舍。#17 列出三条候选路线：

1. 完全不收集任何远端统计，功能取舍只靠 GitLab issue 反馈与本地可测的覆盖率基线。
2. 默认关闭的匿名使用统计，由用户在设置里主动打开。
3. 可选崩溃上报，或只在本机生成崩溃包，由用户决定是否附到 issue。

MenuBarMijia 处理的是住家设备清单、家庭房间、米家与 Home Assistant 凭据。设备型号组合本身就能缩小到具体家庭（同一型号的灯、传感器与路由器是准标识符），所以「匿名统计」在这个产品里比在通用工具里更接近指纹。

现状有三个可以核实的事实：

- 两个客户端都没有任何第三方统计或崩溃 SDK，也没有自建上报端点。仓库依赖只有 SwiftPM 与 npm 常规库，`scripts/check.sh` 的密钥扫描覆盖双端源码与测试目录，跳过 `node_modules` / `target` / `dist` 里的第三方依赖与构建产物。
- 「复制诊断信息」（#45）已经是结构脱敏：`DiagnosticsReportBuilder.Input` 只接受版本、系统、后端、型号与未识别设备，设备 ID、令牌、服务器地址与账号信息在类型层面就进不了报告；`AppSupportDiagnosticsTests.diagnosticsMarkdown` 断言原始 `did` 不出现在输出里。
- `Tests/Fixtures/miot_coverage_golden.json` 把「一份真实 MIoT 规格能合成到什么程度」逐型号钉死，`MiotCoverageBaselineTests` 与 `windows/tests/miotCoverage.test.ts` 两端断言。规格覆盖率在本地可测，不依赖任何使用数据。

## 备选方案

### 方案 1：零远端收集

- **好处**：没有新的网络出口、没有第三方处理者、没有留存与删除政策，也就不存在「匿名化失败」这一整类风险。设置页可以诚实地写「不发送任何统计」。
- **代价**：看不到真实的崩溃率、活跃设备型号分布与功能使用频次。维护者只能读 issue 里愿意写的人反馈，存在「沉默的大多数」偏差。
- **隐私风险**：无。风险转移成了产品判断风险。

### 方案 2：默认关闭的匿名统计

- **好处**：打开的用户能提供崩溃率与功能使用分布，比 issue 反馈更完整；默认关闭在名义上尊重用户选择。
- **代价**：需要一个接收端点与运维，以及去重用的安装标识、上报频率限制、留存与删除流程和隐私政策文案。即便默认关闭，也要为「用户误开」「升级后默认值被改写」「分析 SDK 顺带采集设备信息」分别做验证。
- **隐私风险**：最高。设备型号清单、系统版本与时区组合就足以缩小到具体家庭；「默认关闭」只在用户理解开关含义时才成立。第三方 SDK 的默认采集面通常大于集成时的预期，审计成本长期存在。

### 方案 3：仅本地生成诊断与崩溃摘要

- **好处**：数据不离开本机，用户在粘贴前能逐字审阅，愿意公开多少由用户自己决定。崩溃排查不必等崩溃上报链路搭建完成。
- **代价**：覆盖依赖用户主动操作；摘要不是完整的崩溃分析，最多给出次数与日期。
- **隐私风险**：中。风险点不在传输，而在「生成的文本里混进了路径、用户名、堆栈原文或设备 ID」。必须用类型约束与测试把这类字段挡在报告之外，而不是靠事后正则清洗。

## 决定

采用**方案 1 作为基线**，并在其上加**方案 3 的纯本地模式**。不采用方案 2。

1. **不新增任何远端统计、遥测、崩溃上报或第三方分析 SDK**。应用不自行发起统计请求，设置里也不提供「匿名统计」开关。
2. **功能取舍的证据来源**：GitLab issue 反馈（含模板与分类标签）与 `miot_coverage_golden.json` 覆盖率基线。前者回答「用户要什么」，后者回答「规格支持到哪」。两者都不采集个人数据。
3. **「复制诊断信息」增加本地崩溃摘要**：仅当用户点击按钮时才扫描 `~/Library/Logs/DiagnosticReports`，且只读取目录项的文件名与修改时间。崩溃文件内容从不打开，报告因此不可能带出堆栈原文、用户名或路径。
4. **摘要只输出两个数**：最近 7 天的崩溃次数，以及最近一次的日期（`YYYY-MM-DD`）。无崩溃时次数为 0。文件名、目录路径、设备 ID、账号与崩溃原文都不进入报告；报告结尾的隐私声明同步写明不含崩溃堆栈或文件路径。
5. **筛选规则是纯函数**（`DiagnosticsReportBuilder.crashTimestamps(from:now:window:)`）：文件名以 `MenuBarMijia` 开头，扩展名是 `.ips` 或 `.crash`（不区分大小写），修改时间落在 7 天窗口内。`crashSummary(_:now:window:)` 负责次数与最近时间，窗口常量 `crashReportWindow` 由扫描端与渲染端共用。
6. **不做后台扫描、不落盘、不上传**：扫描结果只活在一次「复制诊断信息」调用里。子目录（如 `Retired`）与非普通文件不计入。
7. **Windows 端保持零收集**。Windows 目前没有通用的「复制诊断信息」入口，只有摄像机诊断；崩溃摘要不在本轮移植范围内，也不以任何形式上报。

## 后果

- 隐私承诺可以写成可核验的一句话：不发送统计，崩溃摘要由用户自己决定是否粘贴。
- 维护者拿不到崩溃率与功能使用频次。取舍依据变成 issue 反馈的质量与覆盖率基线，这意味着团队要把 issue 模板、复现步骤与覆盖率报告维护好，否则决策证据会变薄。
- 本地摘要的价值上限是「有没有崩溃、最近一次是哪天」。需要定位崩溃时，仍要请用户在 issue 里按需附上系统生成的崩溃文件，而这属于用户的自愿披露，不是应用的行为。
- 报告文本新增一段，隐私声明也变长。这是一行 Markdown 的变化，不涉及界面布局，因此现有 UI 快照基线不需要重录。

## 重开条件

只有当以下条件同时成立时才重新评估方案 2：issue 反馈无法支撑一个具体且重要的产品决策；方案 2 的设计能做到显式逐次确认、粘贴前预览完整载荷、可随时删除，并且不引入默认采集范围不受控的第三方 SDK。即使重开，默认值也必须保持关闭。
